ROLES

两个角色：岗位与岗位职责

ROLE 01

岗位（post）

一个 SuperAgent 实例，长期存在，持有外部身份：Kanban 账号、Gitea 账号、ntfy 身份。

扮演 PM 或 Worker，负责一个项目里的一个角色。

长期有身份一个实例
ROLE 02

岗位职责（duty）

岗位内部一次具体任务的一次执行，没有外部身份。

随工单开始，随交付结束；WIP 统计的对象就是它。

一次性无身份一个任务
角色一句话职责主要动作主战场
PM 岗位让项目按流程跑起来颁布宪章 · 派工 · 审进度 · 处理异常面板「编队」页
岗位（Worker）把被派到的职责做完接单 · 执行 · 交付 · 回写看板面板「执行」页
PANORAMA

一分钟全景：一条卡怎么变成交付

Kanban 卡片任务来源
→
指派给岗位assignee = 岗位账号
→
岗位接单读回 + 租约
→
工单（职责）进入执行队列
→
执行会话写代码 / 文档 / memo
→
回写看板状态 + 日志 + 引用

Kanban 是唯一任务源

只有看板上的卡才是任务；评论 @ 岗位不算派工。

Gitea 是代码资产

代码变更的权威载体是 PR；一仓一目录一 PR。

ntfy 是消息通道

实时互通与告警；公开 topic 只作上下文，不构成授权。

MinIO 是扩展存储：文档 / 方案 / memo 的权威载体，由执行会话上传，岗位取回链接回写看板。

ONBOARDING

上线准备：一次做完，两个角色共用

STEP 01

装好、连上

npx.cmd @deepseek-ai/dsh plugin --profile web add "git+https://git.feg.cn/shawoo/superagent"

Windows 用 npx.cmd（PowerShell 会拦 .ps1）；macOS / Linux 用 npx。装完重启 / 刷新，面板出现「超级智能体」，四个来源（Kanban / Gitea / ntfy / MinIO）ready。

STEP 02

三个来源账号

Kanban：地址 + API key（可留空）+ 项目（从列表选）+ 监听列（slug）。

Gitea：地址 + 邮箱 + 密码 + 事件仓库（Issue/PR）+ 宪章仓库（宪章的家，两个仓库分开）。

ntfy：地址 + topic + 入库过滤 tag；MinIO：端点 + 桶。

STEP 03

岗位账号

Kanban 网页手工建号（没有建号 API）：sa-pm-项目 / sa-w1-项目。

记下用户 id；再建 Gitea 账号、约定 ntfy sender。

坑位：看板列名会改，slug 相对稳定——监听请填 slug（如 ready,in-progress），不要填显示名。

ONBOARDING · 三件事

上手只要三步：贴钥匙、登记岗位、发布宪章

看板自己说的，面板不重复设置。

STEP 01

贴一把 API key

设置 → 来源 → Kanban：服务器地址 + API key（可留空：本机存储记录里就有）→ 保存。

面板随即读出工作区、项目与看板真实的列。

STEP 02

登记岗位

从列表选项目（id / 名称 / slug 自动填，主题集默认 pub_<项目 id>）+ 每个岗位的 Kanban 用户 id + 领哪些列 + 并发上限。

Gitea / ntfy 身份可留空——不是编程任务就不需要。

STEP 03

发布宪章

设置 → 项目与岗位 → 宪章：写当期流程与交付标准 → 发布。

发布提交到 Gitea 宪章仓库的 README.md（宪章的家，与事件仓库分开）；版本号 +1、记发布者、旧版进历史；每周至多一版；工单钉在开工那版。

Kanban 是唯一的直接来源：Gitea / ntfy 的事件先入库成看板上的卡（落在 to-do），PM 指派并移进监听列后，才成为职责。没有宪章不可开工：项目在宪章发布前不接受任何任务。

PM · DAILY

PM 岗位的日循环

09:00

清异常队列

编队页异常队列置顶处理：等人回复 → 补上下文；阻塞 → 给结论或拆卡；失败 → 重试或改写描述。

10:00

看在飞职责与 WIP

超限＝先暂停派新卡，判断是卡住了还是上限太小；岗位身份「未设置」就先补账号。

14:00

派工

Kanban 建卡 → 指派给岗位账号 → 放进监听列；不指派＝不派工。

18:00

收工检查

每张卡都回写了状态与日志才算交付；没回写的不要急着关。收工后到 清理 页把已结束职责的工作区集中清掉（有交付物的行要人确认）。

PM · WEEKLY

先复盘，再发宪章：流程是长出来的

周复盘 → 新流程

看板不是固定的任务表，而是一条不断迭代的价值流。

看这一轮的工作日志 → 哪一列总堵、哪一步没意义 → 推荐新的状态 → 与岗位达成共识 → 确认。

确认后先在 Kanban 里加/改列，再在面板 设置 → 项目与岗位 → 宪章 写新版并点「发布」：提交到 Gitea 宪章仓库的 README.md（commit 历史即版本历史），其它 Host 读到同一份。

VALUE STREAM

看板是 VSM：流程与产出都不是固定的

岗位的任务不必然是编程任务，看板也不是固定的列。

PROJECT KIND

项目类型

软件交付 / 销售机会 / 合同管理 / 客诉处理 / 物流投递 / 其他。

类型决定产出长什么样，不是所有卡都要代码。

WORKFACE

工作面

仓库只是工作面之一：文档空间、CRM、表单、看板本身。

非软件岗位不需要 Gitea 身份，有 Kanban 身份就能接单。

DELIVERABLE

产出类型是开放的

卡片用 kind:<类型> 标签声明产出：doc、quote、contract、complaint…

权威载体只有一个，但不限于代码。

⚠ 看板自己的自动化会很快把卡带走（实测：进入 ready 后约 20 秒被搬到 in-progress）——监听列与轮询间隔要跟看板流程的速度匹配；没被接住时，再推一次。

WORKER · CLAIM

接单：只领自己的，并让互斥成立

Kanban 没有 CAS，所以认领必须自己保证互斥。

STEP 01

读回校验

把 assignee 读回来确认是自己；别人的卡不代领、不自领。

STEP 02

写租约

评论追加 lease::<岗位id>，token 用接单时刻。

lease:20261104T1730:w1-fdep
STEP 03

仲裁

同一张卡多条租约时，createdAt 最早的那条获胜，其余退出。

完成后：状态改到 done（按约定列），释放租约，交付物写进评论。

WORKER · DELIVER

执行与交付：产出有唯一权威载体

产出类型权威载体回写看板
代码变更Gitea PR（一仓一目录一 PR）PR 链接 + 评审状态
文档 / 方案MinIO 对象（「MinIO 对象存储」来源卡：端点/桶/凭据，默认取存储记录）对象键 + URL
memo / 决策MinIO 对象（长）或任务评论（短）摘要 + 结论
工作日志Kanban 任务评论（追加式）即为看板内容

交付前自查

✓只改了被授权的仓库与目录
✓产出有可点击引用
✓工作日志已追加
✓状态已更新、租约已释放

边界

开工第一步：用 orchestrator_read charter 读当期宪章（返回版本与载体），不需要 shell/HTTP。

不跨工作目录交付；需求有歧义不要猜：在任务里提问并转 blocked，进入 PM 的异常队列。

文档/方案存 MinIO，不贴进评论：minio_write 到 deliverables/<项目 id>/<ticket id>/<file> → minio_read 回读确认 → 报告写 bucket/key；卡片只留进度与结果。

看板由宿主写：岗位报告 ready，宿主把结果写成评论并把卡片推进交付列；岗位不要自己调用看板 API 搬卡。

ntfy：项目 topic 只有带入库 tag（如 dsh）的消息才入库成卡；没带的当聊天，不产生卡。

CLEANUP

收工之后：集中清理工作区

每个职责都会留下一个工作区和一条 Session；清理是 PM 的收尾动作。

WHERE

「清理」页（PM 视角）

只列已结束职责留下的工作区：按大小排序，标出 Session 数、顶层文件、是否有交付物。

未结束的职责、被别的职责引用的目录，一律跳过。

HOW

先看，再勾，再确认

默认只勾「已结束 + 可清 + 无交付物」；有交付物的行必须人点。

要连目录一起删，单独勾「同时删除工作区文件夹」并在弹窗里确认——不可恢复。

WHAT STAYS

Session 只解除登记

没有受支持的 Session 删除 API：清理只解除工作区登记，日志保留可回放。

stateDir、执行根、盘根与指向执行根之外的符号链接都会被拒绝。

这就是「工作区列表膨胀」的解药：跑得越久，已结束的职责越多，定期清一次比到处找目录省事。

EXCEPTIONS

异常处置表

等人回复

职责在等人。检查提问是否清楚，必要时补上下文或改派。

阻塞

缺权限、缺信息还是外部依赖？给结论，或把卡拆小。

失败

看日志后重试；若反复失败，多半是任务描述不清，改写再派。

长时间无进展

六小时没有更新。ntfy 私聊岗位；仍无响应则人工接手。

CARRIERS · 2026-11-06

环节载体规矩
宪章Gitea「宪章仓库」的 README.md，与事件仓库分开发布 = 提交该文件；commit 历史 = 版本历史；编队页徽标显示载体
任务Kanban 看板（监听列可配，如 to-do）卡片是唯一的派工来源；看板列就是价值流
实时消息ntfy 项目 topic pub_<项目 id>只有带入库 tag（如 dsh）的消息才入库成卡；宿主回复 tag dsh-superagent 不会被回收
数据资产「MinIO 对象存储」来源卡（桶 ateam）非代码交付物：deliverables/<项目 id>/<ticket id>/<file>，卡片只留进度与结果

四张来源卡的凭据默认来自本机存储记录（/BDD/API/AI/dsh/storage/<service>）：留空 = 记录值，填写 = 覆盖；密钥只在宿主内存，不写进设置文件。
