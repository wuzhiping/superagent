ROLES

两个角色：岗位与岗位职责

ROLE 01

岗位（post）

一个 SuperAgent 实例，长期存在，持有外部身份：KanEO 账号、Gitea 账号、ntfy 身份。

扮演 PM 或 Worker，负责一个项目里的一个角色。

长期有身份一个实例
ROLE 02

岗位职责（duty）

岗位内部一次具体任务的一次执行，没有外部身份。

随工单开始，随交付结束；WIP 统计的对象就是它。

一次性无身份一个任务
角色一句话职责主要动作主战场
PM 岗位让项目按流程跑起来颁布宪章 · 派工 · 审进度 · 处理异常面板「编队」页
岗位（Worker）把被派到的职责做完接单 · 执行 · 交付 · 回写看板面板「执行」页
PANORAMA

一分钟全景：一条卡怎么变成交付

Kaneo 卡片任务来源
→
指派给岗位assignee = 岗位账号
→
岗位接单读回 + 租约
→
工单（职责）进入执行队列
→
执行会话写代码 / 文档 / memo
→
回写看板状态 + 日志 + 引用

Kaneo 是唯一任务源

只有看板上的卡才是任务；评论 @ 岗位不算派工。

Gitea 是代码资产

代码变更的权威载体是 PR；一仓一目录一 PR。

ntfy 是消息通道

实时互通与告警；公开 topic 只作上下文，不构成授权。

MinIO 是扩展存储：文档 / 方案 / memo 的权威载体，由执行会话上传，岗位取回链接回写看板。

ONBOARDING

上线准备：一次做完，两个角色共用

STEP 01

装好、连上

npx @deepseek-ai/dsh-superagent@latest install

然后 dsh-superagent status，三个来源都要 ready。

STEP 02

三个来源账号

KanEO：地址 + API key + 项目 id + 监听列（slug）。

Gitea：地址 + 邮箱 + 密码 + 仓库（先测连再保存）。

ntfy：地址 + topic（多实例＝多 topic）。

STEP 03

岗位账号

KanEO 网页手工建号（没有建号 API）：sa-pm-项目 / sa-w1-项目。

记下用户 id；再建 Gitea 账号、约定 ntfy sender。

坑位：看板列名会改，slug 相对稳定——监听请填 slug（如 ready,in-progress），不要填显示名。

THE PANEL

「编队」页：PM 的主战场

PROJECT CARD

项目卡：宪章 + 岗位

徽标显示宪章版本：绿色 vN 本周已发布，黄色过期 需要补发。

每个岗位显示 KanEO 身份、实例、在飞职责 n / limit；超限会红框提示。

身份显示「未设置」＝ 岗位还没建 KanEO 账号，领不到卡。

EXCEPTION QUEUE

异常队列：今天先干这个

等人回复 · 阻塞 · 失败 · 长时间无进展。

点条目直达对应工单；每条都带岗位归属，处理完回看板改状态。

概览页也有队伍摘要（岗位数 / 在飞职责 / 异常数 / 宪章新鲜度）。

PM · DAILY

PM 岗位的日循环

09:00

清异常队列

编队页异常队列置顶处理：等人回复 → 补上下文；阻塞 → 给结论或拆卡；失败 → 重试或改写描述。

10:00

看在飞职责与 WIP

超限＝先暂停派新卡，判断是卡住了还是上限太小；岗位身份「未设置」就先补账号。

14:00

派工

KanEO 建卡 → 指派给岗位账号 → 放进监听列；不指派＝不派工。

18:00

收工检查

每张卡都回写了状态与日志才算交付；没回写的不要急着关。

PM · WEEKLY

先复盘，再发宪章：流程是长出来的

周复盘 → 新流程

看板不是固定的任务表，而是一条不断迭代的价值流。

看这一轮的工作日志 → 哪一列总堵、哪一步没意义 → 推荐新的状态 → 与岗位达成共识 → 确认。

确认后写进宪章新版本，并在面板 设置 → 项目与岗位 → 流程 同步列语义。

version: 5
publishedBy: sa-pm-fdep

# 宪章 v5
- 当期流程（列语义与流转）：
  to-do 待辦池 → ready 待開工
  → in-progress 進行中 → in-review 待評審
  → done 完成
- 角色与职责：PM 管流程与异常；Worker 领自己的卡
- 交付标准：代码 → Gitea PR；文档/方案 → MinIO；
  报价/合同/客诉 → 任务评论 + 状态推进
- WIP 上限：每岗位 3
- 回写规则：状态 + 工作日志 + 产出引用
- 当前工作面集与 topic 集

面板编队页会把看板的列与宪章声明的列并排显示：出现黄色「看板多出的列」＝ 流程长出来了，还没被确认。超过 7 天未更新 → 徽标变黄，提示 PM 补发。

VALUE STREAM

看板是 VSM：流程与产出都不是固定的

岗位的任务不必然是编程任务，看板也不是固定的列。

PROJECT KIND

项目类型

软件交付 / 销售机会 / 合同管理 / 客诉处理 / 物流投递 / 其他。

类型决定产出长什么样，不是所有卡都要代码。

WORKFACE

工作面

仓库只是工作面之一：文档空间、CRM、表单、看板本身。

非软件岗位不需要 Gitea 身份，有 KanEO 身份就能接单。

DELIVERABLE

产出类型是开放的

卡片用 kind:<类型> 标签声明产出：doc、quote、contract、complaint…

权威载体只有一个，但不限于代码。

⚠ 看板自己的自动化会很快把卡带走（实测：进入 ready 后约 20 秒被搬到 in-progress）——监听列与轮询间隔要跟看板流程的速度匹配；没被接住时，再推一次。

WORKER · CLAIM

接单：只领自己的，并让互斥成立

KanEO 没有 CAS，所以认领必须自己保证互斥。

STEP 01

读回校验

把 assignee 读回来确认是自己；别人的卡不代领、不自领。

STEP 02

写租约

评论追加 lease::<岗位id>，token 用接单时刻。

lease:20261104T1730:w1-fdep
STEP 03

仲裁

同一张卡多条租约时，createdAt 最早的那条获胜，其余退出。

完成后：状态改到 done（按约定列），释放租约，交付物写进评论。

WORKER · DELIVER

执行与交付：产出有唯一权威载体

产出类型权威载体回写看板
代码变更Gitea PR（一仓一目录一 PR）PR 链接 + 评审状态
文档 / 方案MinIO 对象对象键 + URL
memo / 决策MinIO 对象（长）或任务评论（短）摘要 + 结论
工作日志Kaneo 任务评论（追加式）即为看板内容

交付前自查

✓只改了被授权的仓库与目录
✓产出有可点击引用
✓工作日志已追加
✓状态已更新、租约已释放

边界

不跨工作目录交付；需求有歧义不要猜：在任务里提问并转 blocked，进入 PM 的异常队列。

MinIO 只有执行会话能写：文档由执行环节上传，岗位取回链接回写看板。

EXCEPTIONS

异常处置表

等人回复

职责在等人。检查提问是否清楚，必要时补上下文或改派。

阻塞

缺权限、缺信息还是外部依赖？给结论，或把卡拆小。

失败

看日志后重试；若反复失败，多半是任务描述不清，改写再派。

长时间无进展

六小时没有更新。ntfy 私聊岗位；仍无响应则人工接手。

KNOWN LIMITS

会撞到的限制（别浪费力气）

限制现象绕法
限流 429大量读写时 KanEO 返回 429退避重试、错开批量写
突发 401偶尔一分钟内鉴权失败等一分钟，脚本已内置退避
看板截断不带 status 查询会按列截断，静默漏任务永远带 ?status= 与 limit=100
assignee 单值一个人只能一个 assignee多人合卡用评论标角色（agent:pm/ux/bi/api）
账号只能 UI 建KanEO 无建号/发 key API在 KanEO 网页手工建号
MinIO 边界岗位（host）访问不了 MinIO执行会话上传，岗位取链接回写
宪章过期超过 7 天未发布PM 周更；岗位接单时记一条提醒
