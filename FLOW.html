FLOW · 从来源到执行的数据与决策流

本文回答三个问题：数据从哪来（来源 → Trigger）、谁在什么条件下接单（准入 → 评估 → 决策）、 接单后怎么执行与回写（工单 → 派工 → worker → 报告 → 回复）。 阅读版：FLOW.html · FLOW.pdf（AIOS 同款深色主题，图已预渲染）。 配套阅读：docs/005-panel.md（来源配置）、docs/007-architecture.md（模块职责）、 docs/003-execution.md（工单阶段表）。

1. 总览

一句话概括：来源只负责把外部事实变成 Trigger；Intake 负责去重与扇出；Evals + 主 Session 负责“接不接”；Tickets 负责“以什么授权接”；DshExecutor 负责“谁、在哪个目录、用什么 Session 去执行”；Replies 负责“结果怎么回去”。

2. 来源层：数据怎么进来

来源角色进入系统的形态是否直接产生任务
Kanban 看板唯一的直接任务来源监听列中的任务 → Trigger（human=true，addressed=direct）✅
ntfy 主题消息入口新消息先建成 Kanban 卡（to-do 池），由看板调度❌（间接）
Gitea（宪章仓库）文档/宪章来源宪章与 duties/ 文本进入评估与 worker 提示词❌
MinIO 对象存储资产/交付物载体worker 通过 MinIO 工具读写；不产生任务❌
飞书 / GitHub可选的事件来源消息 / Issue / PR → Trigger（与 Kanban 同一管道）✅

2.1 Kanban 轮询

  • bootstrap=skip：第一次看到的历史卡只登记、不接单；bootstrap=trigger 则把已有卡也当请求。
  • KV.kaneo.seen：同一任务只产生一次 Trigger，之后靠“卡更新观察”产生增量 Input。
  • 看板观察（observeUpdates）：运行中工单的卡出现评论/标题/描述/列变化 → 生成更新 Trigger（human=true，meta.update=true）→ 作为 Input 送给同一工单的 Session，不新开工单。
  • 看板不裁决、不取消：卡上的状态只作为更新来源；工单要停只能由人在面板点「停止」，卡上的标签/列变化不会停工单（此前的「hold 标签恢复 / 取消列停止」设计已取消）。

2.2 其他来源

  • ntfy：轮询主题历史 → 每条消息调用 Kanban API 建卡（to-do 列）；卡进入看板后才走 Kanban 管道。
  • Gitea：面板“测试连接”与实际健康检查都只校验 charterRepository；它不监听 Issue/PR，卡片的 repo:owner/name 才决定工单用哪个代码仓库。
  • MinIO：s3 来源只做连通/桶探测与工具能力，不产生 Trigger。

3. 摄入 Intake：去重、过滤、扇出

要点：

  1. 先过滤再落库：被来源拒绝的触发也会保存，并带 filtered.reason（面板“被过滤”可查）。
  2. fan-out 到订阅该 Thread 的工单：人写的消息送到（live 工单，或非 human-stop 的已结束工单——后者进入“可复活”队列）。
  3. 没有工单拥有时才评估：owners(trigger) 为空才 queueForEval；否则它只是该工单的 follow-up Input。
  4. human 消息可复活已结束工单：Tickets.wake 在下一轮 evaluateDue 中按当前 Policy 重新验证 Mandate；不通过则 refuse。

4. 评估 Evals：批量、语义强度、截止时间

  • 一个 Thread 一个 Eval：批处理让“同一线程里连续几条消息”只产生一次研判。
  • 截止时间从 candidate 送达算起；paused 时暂停过期，恢复后 deadline 顺延。
  • 过期：重新排队（REQUEUES=2），第三次记为 unavailable（面板显示为问题，可 dismiss）。
  • 主 Session 拿到的是候选卡：线程上下文（threadContext，含仓库/线程读取边界）、批次内其他触发、匹配规则与授权信息。

5. 决策：接不接、以什么强度接

5.1 准入 gate（先后顺序）

Mandate.basis 会记录 source / scope / row / sender / rules / via，用于后续重新验证（Policy 变化、工单恢复）。

5.2 评估换成 outcome

关键语义（常见误解）：off / observe / auto 只决定主动候选（inferred）是否接单； 明确请求（explicit）在任何模式下都会按派工规则路由（src/policy.ts:55、src/app/prompts.ts:45）。 因此“仅观察”下，看板卡进监听列仍会被接单——这是设计行为，不是漏拦。

7. 看板卡的全链路时序（显式请求）

同一张卡在运行中被修改（评论/描述/列）时：observeCards 生成更新 Trigger → Intake → 该工单的 Input → deliver 效果 → worker 在同一条对话里读到，不新开工单。

9. 失败、等待与恢复

注意：blocked/failed 工单收到人的消息后，waitsForPerson 变 false，但当前实现不会因此自动起新 Assignment； 受支持的恢复入口是面板重试。这条边界值得后续改造成“人类消息即恢复”。

9.1 模型服务故障：主 Session 停摆与恢复（看门狗）

模型服务故障（429 预算耗尽、网关不可用）会让主 Session 的那一轮 turn 以 error 结束。此时有两处工作被拿走，且没有任何机制会把它们放回来：

丢失的东西原来的后果现在的恢复方式
relay（工人报告、follow-up、评估候选卡）已投递但模型没读到；effect 行已删除 → 永久丢失看门狗按新的 requestId 再投一次（Sessions.redeliver），模型读到为止
评估（候选卡无人判定）Eval 过期 3 次后记为 unavailable → 请求被丢弃模型恢复后，看门狗用 Engine.reevaluate 重新排队，再判一次

判定依据（src/app/turn-outcomes.ts）：

  • agent/inbox/claimed 告诉我们哪一轮取走了哪条消息；
  • turn/end 的 reason.kind（error/aborted）说明那一轮失败；
  • 该轮没有 assistant/message（spoke === false）说明模型根本没读到那条消息 → 判定为 lost。

面板上的 watchdog 健康条目会说明当前状态：The model service is not answering; the main Session waits for it、 The main Session's turn failed: N relay(s) sent again 或 N request(s) the outage dropped are judged again。 它的价值在于把静默变成可见：以前 429 之后面板什么也不显示。

10. 数据模型

关键字段的用途：

  • Trigger.disposition：记录了它到达了哪些工单、是否被过滤、被谁退还、被哪些工单认领。
  • Thread.subscriptions：之后的触发会 fan-out 给这些工单；context 列出“只读上下文”的工单。
  • Mandate.basis：source/scope/row/sender/rules/via，Policy 变化或工单复活时据此重新验证。
  • Ticket.origin：开单的 Trigger 与批次；execution 决定 worker 目录与 assignment 文本；follows 决定 ready 何时真正结束工单。
  • Assignment.report：最新报告（state/summary/at），waitsForPerson 与 ticketStage 都读它。
  • TicketInput.readAt/deliveredTo：谁在什么时候把哪条输入交给 worker，用于面板与恢复。
